Backend Basics

A backend listens for network requests, validates them, applies business rules, reads or changes permanent data, and returns a response. Its client may be a website, phone app, or another service.

ClientBrowser or app
→
HTTP APIRoutes and JSON
→
ServicesRules and access
→
DatabaseStored records

Responses return through the same layers in reverse.

Important HTTP terms

  • Route: a method and path such as POST /v1/posts.
  • Request: headers, URL values, query values, and optionally JSON.
  • Response: a status, headers, and usually JSON.
  • Middleware: logic around handlers: authentication, logging, timeout, recovery.
  • REST: URLs model resources and HTTP methods describe actions.

Success

200 read/update, 201 created, 204 deleted without a body.

Client errors

400 invalid, 401 unauthenticated, 403 forbidden, 404 missing, 409 conflict.

Go Concepts Used Here

Modules and packages

go.mod names the whole module blog. Each directory is a package, so the service import is blog/internal/service. For a public repository, prefer github.com/yourname/blog-api.

go mod init github.com/yourname/blog-api
go mod tidy

Structs and JSON tags

Structs group fields into entities such as User and Post. JSON tags define property names. The password hash uses a dash tag so it is never serialized.

Interfaces

A repository interface describes storage behavior without selecting PostgreSQL. Services depend on this contract, and tests can provide small fake implementations.

type UserRepository interface {
    Create(context.Context, *User) error
    ByEmail(context.Context, string) (*User, error)
}

Methods, pointers, errors, context

  • A receiver makes a function a method, for example func (s *Auth) Login.
  • *User is a pointer to a shared value instead of a copy.
  • Errors are returned values and must be handled explicitly.
  • errors.Is safely checks wrapped domain errors.
  • context.Context carries cancellation and deadlines through requests and queries.
Avoid mutable global request stateGo handles requests concurrently. Pass dependencies through constructors and request data through arguments or context.

Architecture

This is a modular monolith: one deployable process and database with internal boundaries. This is a strong default and much simpler to operate than early microservices.

Transporthttpapi
→
Applicationservice
→
Contractsdomain
←
Adapterpostgres

Dependencies point inward. Domain does not know about HTTP or PostgreSQL.

Domain

Entities, stable errors, and repository contracts.

Services

Validation, hashing, tokens, publishing, pagination, and permissions.

Repositories

Parameterized SQL, transactions, and database error mapping.

Transport

Routes, JSON, bearer authentication, and HTTP statuses.

Thin handlers are easier to test and change. Business rules remain independent of HTTP and SQL. Do not add abstractions without a real responsibility; this project intentionally avoids generic repositories, event buses, and microservices.

Folder Structure

cmd/api/ main.go wiring, server, shutdown internal/ config/ environment configuration domain/ entities, errors, contracts service/ application rules repository/postgres/ SQL implementations platform/database/ connection pool transport/httpapi/ routing, middleware, JSON migrations/ versioned schema docs/ guides and API reference go.mod / go.sum module and dependency locks Dockerfile / compose.yaml local containers Makefile / .env.example developer commands and config

Go enforces the internal boundary, so outside modules cannot import these private packages. main.go stays small because it only constructs dependencies and controls process lifecycle.

One Request End to End

For POST /v1/posts:

  1. Chi matches the method and route.
  2. Middleware adds request ID, client IP, recovery, timeout, logging, and JWT verification.
  3. JWT claims provide the authenticated user ID and role.
  4. The handler limits the body to 1 MiB, rejects unknown JSON fields, and creates a service input.
  5. The service validates fields, creates UUID and slug, normalizes tags, sets publication time, and enforces rules.
  6. It calls the domain repository interface.
  7. The PostgreSQL adapter begins a transaction, inserts the post and tags, then commits.
  8. The handler returns JSON with 201 Created.

Dependency injection

main.go constructs repositories and passes them into services. Services never open their own database. This makes dependencies visible and replaceable in tests.

users := postgresrepo.NewUsers(db)
posts := postgresrepo.NewPosts(db)
tokens := service.NewTokenManager(secret, tokenTTL)

authService := service.NewAuth(users, tokens)
postService := service.NewPosts(posts)

Database Design

  • users: identity, bcrypt hash, display name, role.
  • posts: content, author, category, status, slug, timestamps.
  • categories: optional classification for a post.
  • tags and post_tags: reusable many-to-many labels.
  • comments: responses belonging to one user and post.

Constraints reject duplicate email addresses and slugs, invalid statuses and roles, and published posts without a publication time. Multi-table post/tag writes use a transaction, so partial changes roll back.

Indexes support public feeds, author/category queries, and visible comments. Add indexes for measured query patterns and verify them with EXPLAIN ANALYZE.

Never edit an applied production migrationCreate a new numbered migration. Changing old history makes environments disagree.

Run the Project

Docker Compose

Install and start Docker Desktop, then run from the repository:

docker compose up --build

This starts PostgreSQL, waits for health, applies migrations, builds the API, and exposes http://localhost:8080.

docker compose down
docker compose down -v   # also permanently deletes local data

Local Go and PostgreSQL

  1. Install Go 1.23+ and verify go version.
  2. Install PostgreSQL and create the blog database/user.
  3. Apply migrations/000001_init.up.sql.
  4. Copy .env.example to .env and update its values. This project loads that file automatically; real process environment variables take precedence.
  5. Run dependencies and the API.

PowerShell

$env:HTTP_ADDRESS = ":8080"
$env:DATABASE_URL = "postgres://blog:blog@localhost:5432/blog?sslmode=disable"
$env:JWT_SECRET = "replace-this-with-a-long-random-secret"
go mod download
go run ./cmd/api

DATABASE_URL and JWT_SECRET are required. The secret needs 32+ characters. Other settings control token lifetime, server address, connection pool size, and shutdown timeout.

Build It Yourself Next Time

Build vertical working slices. Every step should leave the application compiling.

  1. Requirements: define users, roles, resources, permissions, public/private data, and non-goals.
  2. API contract: decide routes, fields, statuses, and errors.
  3. Data model: decide tables, relationships, constraints, deletion behavior, and indexes.
  4. Module: run go mod init and create cmd/api/main.go.
  5. Configuration: validate required values at startup.
  6. Domain: create types, errors, and repository interfaces for one feature.
  7. Service: write business behavior and unit tests with fakes.
  8. Repository: add parameterized SQL, transactions, and error mapping.
  9. Transport: decode, call service, encode; keep handlers thin.
  10. Wiring: construct concrete dependencies in main.
  11. Verification: format, test, vet, then repeat.
  12. Integration: prove migrations and SQL against disposable PostgreSQL.
health -> registration -> login -> authentication
-> create post -> public reads -> ownership updates
-> comments -> administration -> production hardening

Ask before coding

  • Who may perform this operation?
  • Which fields are required, optional, unique, or immutable?
  • What happens under concurrent requests?
  • Does it need a transaction?
  • Could private data leak?
  • What errors should callers receive?
  • How will success and failure be tested?
  • How does the schema migrate and roll back?

Testing

internal/service/service_test.go uses fake repositories to test normalization, bcrypt, JWT claims, validation, post publication, tags, and ownership without PostgreSQL.

go test ./...
go test -cover ./...
go test ./internal/service -run TestCreatePublishedPost
go test -race ./...   # requires CGO/C compiler

Add real PostgreSQL tests for constraints, transactions, cascades, ordering, visibility, and pagination. Add httptest coverage for status codes, auth, body limits, and error JSON.

Testing pyramidUse many fast service tests, focused repository integration tests, and fewer end-to-end tests for critical user journeys.

Security

Passwords

Never store or log plaintext. Use bcrypt and never serialize hashes.

Authorization

Authentication identifies a user; authorization checks access to this resource.

SQL

Use placeholders such as $1. Never concatenate request data.

Secrets

Keep passwords and keys out of Git and use a secret manager.

  • Use HTTPS in production.
  • Use short access tokens and rotating refresh tokens for long sessions.
  • Rate-limit login, registration, and comments.
  • Do not expose internal SQL errors.
  • Restrict browser CORS to trusted origins.
  • Validate maximum content length.
  • Scan dependencies and images.
  • Back up PostgreSQL and prove restoration works.
Before public launchAdd rate limiting, refresh-token revocation, email verification, password reset, and signing-key rotation.

Production

  1. Build immutable images in CI.
  2. Run format, vet, tests, race detection, vulnerability, and migration checks.
  3. Use managed PostgreSQL with TLS, backups, monitoring, and recovery.
  4. Keep secrets in a platform secret manager.
  5. Run migrations as a controlled release step.
  6. Terminate HTTPS at a trusted proxy/load balancer.
  7. Run multiple stateless API instances.
  8. Collect structured logs, metrics, traces, errors, latency, and pool statistics.
  9. Configure liveness and readiness; /healthz is database-backed readiness.
  10. Practice rollback.

For schema changes, use expand-and-contract: add compatible schema, deploy compatible code, backfill, switch reads, then remove old schema in a later release.

Common Mistakes

  • Putting everything in main.go.
  • Ignoring returned errors.
  • Accepting author ID from JSON instead of verified claims.
  • Authenticating without checking resource ownership.
  • Returning drafts in public queries.
  • Concatenating SQL.
  • Missing request and shutdown timeouts.
  • Unbounded pagination.
  • Logging secrets or tokens.
  • Editing applied migrations.
  • Starting with microservices.
  • Adding abstractions without a real boundary.
  • Using only mocks and never testing SQL.

What to Add Next

  1. GET /v1/me: add user lookup by ID through every layer.
  2. Author drafts: list only the current author's private posts.
  3. Category administration: add admin-only CRUD; the table exists.
  4. Integration tests: establish confidence first.
  5. Refresh tokens: hashed, rotating, revocable sessions.
  6. Email workflows: verification and password reset.
  7. Media: object storage, with metadata in PostgreSQL.
  8. Cursor pagination and search: introduce as volume requires.
  9. Moderation and audit logs.
  10. Outbox worker: reliable mail and event processing.
Best first exerciseImplement GET /v1/me: add UserRepository.ByID, SQL, service method, protected handler, route, and tests. It touches every layer without changing the schema.

Glossary

API: a defined way for systems to communicate. CRUD: create, read, update, delete. JWT: signed claims such as user ID, role, and expiration. Migration: versioned schema change. Repository: storage abstraction. Slug: URL-friendly title identifier. Transaction: operations that commit or roll back together. UUID: globally unique record ID. Dependency injection: passing dependencies into a component rather than constructing them inside.
